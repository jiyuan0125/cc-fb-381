运单在途指标 —— 计算口径说明
================================

本文件说明 materialize.py 刷新 metrics 表时采用的业务口径，供人工核对。
数据源：waves/ 目录下的波次 csv（列：运单号、时间、节点、城市）。
产物：metrics.db 中的 metrics（每运单一行）、events（去重后的原始轨迹）、wave_runs（波次处理记录）；
运行日志：run_log.txt（每轮追加）。


一、时效从哪里起算
------------------
口径 1：起点时间 = 该运单**最早的一条 P（揽收）节点的轨迹时间**。

理由：揽收是承运方责任起点，中转/派送节点先到或补录都不改变起算点；同一运单有多条 P（如多段揽收补录）取最早一条。

口径 1b（兜底）：轨迹里**一条 P 都没有**（中转站数据先到、揽收数据尚未进系统）时，
起点时间 = 该运单当前**最早一条轨迹的时间**，origin_node 记为那条轨迹的节点码（非 P 开头）。
这种行的起点会随揽收数据补到而**向前修正**，已用时效随之变大，属预期行为。
本次数据中没有出现这种运单（60 单全部有 P），但规则保留。

已用时效 elapsed_hours =（最后节点时间 − 起点时间）÷ 3600，保留 2 位小数，单位为小时。
注意：按"事件时间"差计算，不用系统当前时间，因此中途积压不再补跑不会让时效虚增；
幂等重跑也不会改变数值。

二、退回再派的运单怎么算全程
----------------------------
口径 2：**不重置、不截断**。全程 = 从首次揽收（起点时间）到当前最后节点，包含退回段和二次派送段，
退回在分拨的停留、退回运输时间全部计入已用时效。

理由：客户视角关心的是"下单到最终结果的墙钟时长"，退回是这条链路真实发生的成本；
若按第二次派送重新起算，会掩盖退回造成的时效损失，也无法与未退回运单横向对比。
另单独落 return_count 列（R 类节点条数），便于把退回单单独拉出来看。

三、其他字段
------------
last_node / last_city / last_event_time：按事件时间取**最大**的一条轨迹（不是最后到达系统的那条），
保证波次乱序/重复投递时结果稳定。
node_count（途经节点数）：该运单全部轨迹的条数（同一节点码在不同时间出现算多条，如 WB100013 的 D08 出现两次算 2）。
去重后计数，重复投递的同一事件只算一次。

状态 status（按当前最后节点判定）：
  已签收      最后节点为 S
  退回中      最后节点为 R*（已进入退回流程，尚未重派/签收）
  退回重派中 出现过 R*、且最后节点不是 R/S（退回后已重新进入中转或派送）
  派送中      最后节点为 D*
  运输中      最后节点为 T*
  已揽收      最后节点为 P*（尚未离开揽收环节）
顺序：S > R > (历史有 R) > D > T > P。
已知边界：若签收之后又补来一条时间更晚的 D/T 轨迹（数据异常），状态会按"时间最大"回到派送中/运输中，
不做"已签收锁定"的特殊处理——口径以时间轴为准，异常数据应由上游修正。

四、去重与幂等（同一波次重复投递不重复累计）
--------------------------------------------
- 事件唯一键：(运单号, 时间, 节点, 城市)。events 表以该键为主键（WITHOUT ROWID），
  重复事件 INSERT 冲突即跳过，指标按 events 全量重算，不会累加。
- 同波次重投：wave_runs 记录 (wave_id, 文件内容 SHA-256)。波次号与内容哈希都相同 → 整波跳过，
  日志记一条 skipped 行，不更新指标。
- 同波次但内容变了（补录/重发）：只处理新增事件，只刷新受影响运单，日志中 dup_events 会显示重复行数。
- 每波次在一个 SQLite 事务内写入 events + metrics + wave_runs，异常中断不会留下半波数据。
- 非法行（时间格式错、节点码不符合 P/T/D/R+两位数字 或 S、空字段）跳过，计入日志 bad_rows，
  不影响同波次其他数据。

五、运行日志 run_log.txt
------------------------
每轮每波追加一行：
  时间 | wave=波次号 | file=路径 | rows=解析行数 | new_events=新增事件 | dup_events=重复事件
       | updated_waybills=当轮更新的运单数 | status: 该批运单的最新状态分布
跳过整波时行内为 "skipped: ..." 且 updated_waybills=0。
波次处理明细同时落库在 wave_runs 表（含内容哈希和处理时间），便于核对。

六、人工核对示例（可对照 events 表复算）
----------------------------------------
WB100013（第一次派送失败后退回分拨、二次派送签收）：
  07:33 P03 揽收 → 08:13 T06 → 08:54 D08 → 09:35 R02 退回 → 10:24 T05 → 11:07 D08 → 11:48 S
  起点 07:33（最早 P），全程 4.25 小时，途经 7 条轨迹，return_count=1，状态 已签收。
WB100020（退回后重派中，尚未签收）：
  09:05 P04 → 09:56 T05 → 10:49 D08 → 11:47 R01 → 12:34 T02 → 13:20 D08
  起点 09:05，全程 4.25 小时，状态 退回重派中。
WB100024（同一中转节点两条时间不同轨迹）：
  06:35 P09 → 07:36 T05 → 08:19 T05 → 08:37 D05 → 10:20 S，途经 5 条，全程 3.75 小时。

核对 SQL：
  单票轨迹：SELECT event_time,node,city FROM events WHERE waybill='WB100013' ORDER BY event_time;
  起点复核：SELECT MIN(event_time) FROM events WHERE waybill='WB100013' AND node LIKE 'P%';
  全表快照：SELECT * FROM metrics ORDER BY waybill;
  波次记录：SELECT * FROM wave_runs;
  重复行复核（同波次内重复）：awk -F, 'NR>1' waves/2026091514.csv | sort | uniq -d
